# Architecture — POS & Inventory Management System

Three separate PySide6 desktop applications sharing one backend:

- **`pos_app`** — Branch POS. Cashier-facing: barcode-scanner input, cart, checkout, thermal receipt. Strictly sales — it only ever *deducts* stock, via a finalized `Transaction`.
- **`depot_app`** — Warehouse/Depot. Warehouse-staff-facing: receiving new inventory (adds stock) and dispatching goods out for reasons other than a sale (removes stock). Also the primary, prominent home for critical-stock alerts.
- **`admin_app`** — Admin Dashboard. Manager-facing: product CRUD, global price updates, sales reports (PDF/Excel), and a passive inventory-health view.

All three connect to a single shared SQLite database file (`shared_backend.db`, WAL mode) that stands in for a future hosted backend (e.g. Supabase). The layering below is designed so that migration only ever touches `database/`.

## Layers

| Layer | Package | Responsibility |
|---|---|---|
| Data models | `shared/models.py` | Plain dataclasses (`Product`, `Transaction`, `LineItem`). No I/O. |
| Data access | `database/` | The *only* package allowed to run SQL or open `shared_backend.db`. Exposes repository functions returning/accepting `shared.models` instances — never raw rows, never a connection object. |
| Builders | `shared/builders/` | Pure functions: data in, a renderable/document object out (`ReceiptDocument`, `ReportDocument`). No printing, no file writes, no Qt imports. |
| GUI | `pos_app/gui/`, `depot_app/gui/`, `admin_app/gui/` | Screens and widgets. Calls into `database/` (via each app's `services/`) and renders builder output. Never contains SQL. |
| Export | `pos_app/export/`, `admin_app/export/` | Takes builder output and performs the actual I/O — printing, PDF, Excel. `depot_app` has no export layer yet (no document output required by its current scope). |
| Shared GUI mechanics | `shared/gui_kit/` | Generic, app-agnostic base classes only (see below). |

Nothing outside `database/` touches storage directly. Nothing outside `shared/builders/` decides how a receipt or report is laid out. This is what lets the same builder output feed an on-screen preview and a real export with zero duplication.

**Layering rule made explicit now that there are three peer apps:** `pos_app`, `depot_app`, and `admin_app` never import from one another — only from `shared/` and `database/`. Where two apps happen to need similar-looking code (e.g. both POS and Depot want a large touch-friendly button), each keeps its own copy in its own `gui/components/` rather than one importing the other's. A small amount of duplication here is the deliberately cheaper alternative to a cross-app dependency, which is expensive to unwind later and makes it possible to build/install/version one app without the others.

## The core entities

- **`Product`** — `barcode` (PK), `name`, `price`, `stock_quantity`, `critical_stock_level`.
- **`Transaction`** — a finalized sale: a list of `LineItem`s (each capturing product name/price *at time of sale*, so later price edits never rewrite sales history) plus a computed `total`. Finalizing a transaction atomically deducts stock (`database/transaction_repository.py`). The only writer: `pos_app`.
- **`StockMovement`** *(row shape, not yet a `shared.models` class — see `database/inventory_repository.py`)* — a `receive` or `dispatch` event: `product_barcode`, `quantity`, an optional `note`, `created_at`. Every non-sale stock change gets one of these, atomically with the `products.stock_quantity` update it caused. The only writer: `depot_app`.

Between them, `Transaction` and `StockMovement` account for every way `products.stock_quantity` can change — a sale, a receipt, or a dispatch, never a silent edit (see `product_repository.update()`'s docstring).

## Why `shared/` holds more than models

`shared/` is defined by one rule: **zero storage/network dependency**. Anything meeting that bar and needed by more than one of `database/`, `pos_app/`, `depot_app/`, `admin_app/` belongs here, once:

- `models.py` — so GUI code can reference `Product`/`Transaction` without importing the data-access layer.
- `constants.py` — colors, fonts, spacing, page sizes, the shared DB filename, the alert poll interval. Single source of truth; nothing outside this file redefines these.
- `paths.py` — frozen-aware path resolution (see Packaging below): where bundled resources live once packaged, and where the three independently-installed apps find the same shared database.
- `i18n.py` — a single `tr(key)` lookup, so every UI string routes through one place from day one.
- `theme.py` — one dark palette + one light palette dict, and the one `apply_theme()` function that applies either (or, since the UI redesign below, an app's own custom palette dict passed in explicitly). Nothing outside this file should call `setStyleSheet()` with base palette colors directly.
- `builders/` — pure document builders, described above.
- `gui_kit/` — **mechanics only** (see next section). Not styled components.

## Why the apps' GUI components are *not* all in `shared/`

POS, Depot, and Admin have genuinely different ergonomics: POS and Depot both need large, high-contrast, fast-tap targets for staff working scanner-in-hand; Admin needs compact, dense layouts for a manager reviewing many records at once. Forcing one shared component library onto all three would mean either the floor apps' buttons are dangerously small for fast use, or Admin's screens waste space on touch-sized targets it doesn't need. POS and Depot happening to want similarly-sized buttons is *not* a reason to share a component between them either — see the layering rule above: each keeps its own copy.

So the split is:

- **`shared/gui_kit/`** — only the generic *mechanism*, framework-level, with no opinion on size, density, or what interval to poll at:
  - `popup_window.py` — `RefreshablePopup` base class: a popup that redraws itself in place (`open_or_refresh()`) instead of stacking a new window each time it's invoked.
  - `visual_tab.py` — `VisualTab` base class: a tab that lays out one primary visual plus its controls in normal document flow (`QVBoxLayout`), so action buttons are never floated as an overlay on top of other interactive elements.
  - `polling.py` — `PollingTimer`: re-runs a callback on an interval and emits its result. New with `depot_app` (see Alert Mechanics below) — added here rather than inside `depot_app` because `admin_app`'s Inventory Health tab or a future POS refinement could equally use it; it was designed generic from the start rather than extracted later.
- **`pos_app/gui/components/`** — `ActionButton` (large, high min-height, tuned for fast taps) and `StockAlertBanner`.
- **`depot_app/gui/components/`** — its own `ActionButton` (same philosophy as POS's, separate file) and `CriticalStockRow` (one row of the low-stock list).
- **`admin_app/gui/components/`** — `CompactButton` (small, dense) and `DataTable` (a `QTableView` wrapper for product lists, report rows, and the Inventory Health table).

All three `components/` packages subclass/use `shared/gui_kit` mechanics but own their sizing. Base palette colors and typography tokens are shared (`shared/theme.py`, `shared/constants.py`); pixel sizes, padding, and touch-target dimensions are not — each app's `components/__init__.py` says so explicitly.

## Alert mechanics: why Depot gets the alert and Admin doesn't

This was a deliberate behavioral split, not a data split — `depot_app` and `admin_app` query the exact same thing (`product_repository.get_critical_stock_list()`), just to different effect:

- **`depot_app/gui/low_stock_panel.py`** is the *first/default tab* of the Depot app — not one tab among several, but what warehouse staff land on. It re-runs `get_critical_stock_list()` on an interval via `shared.gui_kit.polling.PollingTimer` (`shared.constants.CRITICAL_STOCK_POLL_INTERVAL_MS`, 15s by default) and stays current while the app sits open. This is Depot's whole reason for existing in the alert flow: POS deducts stock silently at checkout, and Depot is where that has to surface into something a person acts on — reorder, or dispatch from another location.
- **`admin_app/gui/inventory_health_tab.py`** is one passive tab among Products / Price Updates / Sales Reports / Inventory Health, no polling, no prominence. A manager opens it to review the overall picture on their own schedule. No popups, ever — the brief was explicit that Admin should not be interrupted by operational alerts.

**A technical constraint worth being explicit about:** SQLite has no cross-process push mechanism (no Postgres-style `LISTEN`/`NOTIFY`). `pos_app`, `depot_app`, and `admin_app` are three separate OS processes — when POS deducts stock, nothing tells Depot; Depot can only find out by asking again. So Depot's "real-time" alert is, mechanically, polling every 15 seconds, not a push notification. That's what `PollingTimer` is — the mechanism name is honest about what's actually happening. If truly instant alerts become a requirement later, that needs actual IPC (a local socket, a file-watcher on the WAL file, or skipping straight to a hosted backend with real push) — worth flagging now rather than let "polling" quietly get assumed to mean "live" during implementation.

`depot_app/gui/main_window.py` also flags an open, not-yet-decided UX question for the next slice: whether the always-visible panel is enough, or whether a newly-crossed-critical item should also get a brief toast popup on top of it. Noted rather than guessed, since it's a real UX call, not an architectural one.

## Why PySide6

All three apps need the same framework for a consistent look via one shared QSS-based theming system, but they lean on it differently: Admin's product lists and sales reports want real model/view table widgets (`QTableView` + `QAbstractTableModel`) for sorting/filtering data-dense grids; POS and Depot want a small number of large, fully-custom-styled buttons and (for Depot) a `QTimer`-driven refresh. PySide6 covers all of this without needing a second toolkit, and its LGPL license keeps it free for any use. (PyQt6 is functionally equivalent but GPL/commercial-licensed.)

## Database: WAL mode and the migration path

`database/connection.py` opens `shared_backend.db` in WAL journal mode with a `busy_timeout`, which is what lets all three apps (as separate OS processes) read and write it concurrently without one blocking the others on ordinary contention — a writer that briefly loses a race retries instead of failing the whole checkout (or receipt, or dispatch) outright.

`database/schema.sql` is the single source of truth for table structure: `products`, `transactions` + `transaction_items` (POS), `stock_movements` (Depot), and every later domain's tables. It only ever says `CREATE TABLE IF NOT EXISTS`, which can't add a column to a table an older database already has - so **`database/migrations.py`** runs right after it (from `connection._ensure_schema()`): it reads SQLite's `PRAGMA user_version`, and for each step above it adds the missing columns and does that step's one-time data work, inside one `BEGIN IMMEDIATE` together with the version bump (re-checking the version after taking the lock, so POS, Depot and Admin starting at once against an old file migrate it exactly once). New databases get the columns straight from `schema.sql`; the step then only stamps the version. Indexes on migrated columns live in `migrations.py`, since on an old database `schema.sql` runs before the columns exist. When this MVP eventually moves to a hosted backend, the intended migration path is: rewrite `database/` (repository functions keep the same signatures, same `shared.models`/row-dict return shapes) and touch nothing in `shared/`, `pos_app/`, `depot_app/`, or `admin_app/`.

## Packaging: three independent installers, one shared data location

`pos_app`, `depot_app`, and `admin_app` build and install as three completely independent Windows applications — separate `.exe`s, separate Program Files folders, separate uninstall entries — because a cashier workstation should never need Depot's or Admin's code sitting on it, and so on for each pairing. That independence creates one real problem: once installed, there's no more shared repository folder on disk for the three processes to agree on where `shared_backend.db` lives. `shared/paths.py` is what solves it, and it's the reason `database/connection.py` no longer computes a path relative to the source tree:

- **`get_db_path()`** resolves a single machine-wide location — `%ProgramData%\POSInventorySystem\shared_backend.db` by default — via a small `config.json`. All three apps read the identical file, regardless of which one created it or where any was installed. This was a deliberate choice among three options (same-machine fixed path / networked from day one / configurable-defaulting-local); configurable-defaulting-local was picked so today's single-PC MVP needs zero setup, while a later multi-workstation layout (POS at the register, Depot in the warehouse, Admin in the back office, all pointed at a network share) is a config change via `set_db_path()`, not a rebuild. **Where that `config.json` actually lives now has two possible answers** — see Mass Deployment below, which is the reason `_config_path()` checks more than one location.
- **`resource_path()`** resolves bundled resources (currently just `database/schema.sql`) whether the code is running from source or from a frozen PyInstaller build (`sys._MEIPASS`). Any new file an app needs to read off disk at runtime — not user data, a bundled resource — goes in `shared/build_manifest.BUNDLED_DATA_FILES`, the single list both the `.spec` files and `deploy_system.py` read, rather than being added to either independently (see Mass Deployment below for why that mattered enough to extract).

Each app's packaging lives entirely inside its own folder, so nothing about building or installing one app touches the others:

```
pos_app/
├── pos_app.spec              # PyInstaller spec — bundles main.py + shared/ + database/
├── build_exe.bat             # -> pos_app/dist/BranchPOS/
├── installer/
│   └── pos_app_installer.iss # Inno Setup script -> pos_app/installer_output/
├── dist/                     # PyInstaller output (generated, gitignored)
├── build/                    # PyInstaller intermediate (generated, gitignored)
└── installer_output/         # compiled Setup.exe (generated, gitignored)
```

`depot_app/` and `admin_app/` mirror this exactly (`depot_app.spec`/`DepotApp.exe`/`depot_app_installer.iss`, `admin_app.spec`/`AdminDashboard.exe`/`admin_app_installer.iss`). All three installers use `PrivilegesRequired=lowest` (no UAC prompt) and a `[Run]` entry that offers to launch the app immediately after install — a cashier, warehouse worker, or manager runs the installer and clicks through, nothing more. All three `.iss` scripts carry a fixed, unique `AppId` GUID each (required for Inno Setup to recognize a future version as an upgrade rather than a separate install) — generated once and not meant to change after an app ships.

Building requires `pip install -r requirements.txt` (adds `pyinstaller`) plus a separate, free install of [Inno Setup](https://jrsoftware.org/isinfo.php) for the `iscc` compiler — that second tool isn't something pip can install. See `README.md`'s Building section for the exact commands.

## Mass deployment: `deploy_system.py`, and why `config.json` can live in two places

The installer-based packaging above answers "install one clean copy of one app on one machine." It doesn't answer "I need `POS_1.exe` through `POS_4.exe` on four different tills, `Depot_1.exe` on the warehouse PC, and `Admin_1.exe` in the office, built and named in one pass, with nothing to move around by hand except copying the finished files out." `deploy_system.py` (repo root) is that second, separate path — an interactive CLI wizard that:

1. Asks how many instances of each app to generate, and what shared database path to use.
2. Builds each app **once** via `sys.executable -m PyInstaller <entry>.py --onefile --noconsole` (not the onedir `.spec` files — a deliberately different PyInstaller invocation, described below) — never a bare `pyinstaller` on PATH, for the identical wrong-interpreter reason `build_exe.bat` guards against.
3. Copies that one built `.exe` as many times as requested into a single flat `GPUSA/dist/` folder, renamed `Admin_1.exe`, `POS_1.exe`, `POS_2.exe`, etc. — wiping any previous `dist/` contents first, so the folder always exactly matches the latest run's request.
4. Writes exactly one `dist/config.json`, shared by every `.exe` in that folder, containing the database path from step 1.

**This is intentionally a second build configuration, not a reuse of `pos_app.spec` etc.** — those are onedir (`COLLECT`) builds by design (faster startup, fewer antivirus false positives; see the earlier packaging decision), while this explicitly asked for `--onefile`. Rather than let the two configurations' bundled-resource lists drift apart from each other over time, both now import `shared/build_manifest.BUNDLED_DATA_FILES` — currently just `database/schema.sql` — instead of hardcoding it twice. Add a new bundled resource there once; both build paths pick it up.

**Why `config.json` needed a second lookup location.** The installer-based apps each land in their own Program Files folder with nothing else beside them, so they've always resolved `config.json` from the machine-wide `%ProgramData%\POSInventorySystem\` fallback. `deploy_system.py`'s output is different by construction: every instance sits *directly next to* a single shared `config.json`, and when you then copy one instance out to its target machine (say, `POS_2.exe` to till #2), the natural, zero-extra-step thing is to copy `config.json` right along with it — no `%ProgramData%` write needed, no dependency on which app happened to run first on that machine. So `shared/paths.py`'s `_config_path()` now checks **exe-adjacent first, `%ProgramData%` second**:

```python
def _config_path() -> Path:
    exe_adjacent = _exe_adjacent_config_path()   # dirname(sys.executable), only when sys.frozen
    if exe_adjacent is not None and exe_adjacent.exists():
        return exe_adjacent
    return get_shared_data_dir() / _CONFIG_FILENAME   # %ProgramData% fallback
```

The frozen check matters: in a normal `python -m pos_app.main` dev run, `sys.executable` is the Python interpreter, not the app, so treating its directory as a config location would be wrong — `_exe_adjacent_config_path()` returns `None` unless `sys.frozen` is set (true only inside a PyInstaller-built `.exe`), and dev mode goes straight to the `%ProgramData%` path exactly as before. An installer-built app that happens to have no `config.json` beside it (the normal case) also falls straight through to `%ProgramData%` — this is additive, not a behavior change for the installer-based deployment.

**Practical implication for you:** an instance built by `deploy_system.py` and moved to a new machine needs its `config.json` to travel with it (or an equivalent one already sitting next to it, or nothing at all if `%ProgramData%\POSInventorySystem\shared_backend.db` on that machine is actually the intended path — in which case it'll fall back there and just work). If you ever run `deploy_system.py`'s wizard again with a *different* database path, remember it wipes and regenerates `dist/` and its single `config.json` from scratch — instances already copied out to machines keep whatever `config.json` they took with them; re-running the wizard doesn't reach out and update them.

## Two-stage installer: `build_setup.py` + `installer.py` → `build.exe` + `setup.exe`

`deploy_system.py` above is still the fastest path for the developer's own local testing, and it isn't going away. But handing `POS_2.exe` plus a loose `config.json` to a branch manager and trusting both files stay together is fragile once they're outside the room — this third path packages the *whole wizard* into one file, and it's the recommended way to distribute to anyone outside the dev team. The whole system is two source scripts and two compiled tools, one building the other:

- **`build_setup.py`** (repo root, developer-only): builds `admin_app`, `pos_app`, and `depot_app` each as a onefile `--noconsole` .exe (same `shared/build_manifest.BUNDLED_DATA_FILES` approach as `deploy_system.py`), then compiles `installer.py` into `Kurulum/setup.exe` — **without** `--noconsole`, since `installer.py` is a text wizard and needs its console visible — embedding all three built app `.exe`s inside it via `--add-data ... payload`. Run directly (`python build_setup.py`) or, more conveniently, as **`build.exe`** — see below.
- **`installer.py`** (repo root, compiled *into* `setup.exe`, never run directly): a deliberately dependency-free script — no `shared`, no `database`, no PySide6 — since at runtime it has no source tree beside it, only what PyInstaller extracted. At startup it reads `sys._MEIPASS/payload/` (set by the PyInstaller bootloader only inside a running frozen onefile build) to find the three bundled app exes, asks how many Admin/POS/Depot instances to install and what shared database path to use (with an explicit warning: pressing Enter is only safe when every instance being installed *right now* runs on this same machine — across machines it silently gives each one its own disconnected database), then copies/renames the requested exes plus one `config.json` into `Path.cwd()` — wherever `setup.exe` was double-clicked. Every exit path runs through a `pause_and_exit()` helper, since a double-clicked console `.exe`'s window vanishes the instant the process ends otherwise.
- The output folder shape (`config.json` sitting next to numbered app exes) is identical to `deploy_system.py`'s `dist/` output, so `shared/paths.py`'s exe-adjacent-first `_config_path()` (documented above) already handles it with zero further changes.

**`build.exe`: a convenience wrapper, not a second standalone tool.** `make_build_exe.bat` compiles `build_setup.py` itself into `build.exe` at the repo root, so day-to-day you can double-click `build.exe` instead of typing `python build_setup.py` — they do exactly the same thing. This is deliberately the *lighter* of two possible designs: `build.exe` still has to run from inside a full GPUSA checkout with the venv active, because it shells out to an external `python -m PyInstaller` to compile the three apps and `installer.py`, exactly like the unfrozen script does. It does **not** bundle PyInstaller or the app source *inside itself* to become a truly standalone build tool — that was considered and deliberately deferred, since only the developer ever runs it and the added complexity (an in-process PyInstaller invocation instead of a subprocess, source files embedded as bundle data, keeping that in sync as PyInstaller/PySide6 change) isn't worth it for a single-user convenience. Three details only matter once `build_setup.py` is frozen this way, and all three mirror problems `shared/paths.py` already solves for the shipped apps:

- **Finding the repo**: `__file__` inside a frozen bundle doesn't point at `build.exe`'s real location, so `build_setup.py` resolves `REPO_ROOT` from `sys.executable`'s directory when `sys.frozen` is set (same pattern as `_exe_adjacent_config_path()`) — which is why `make_build_exe.bat` builds `build.exe` straight into the repo root, not a `dist/` subfolder.
- **Finding the right `python`**: `sys.executable` inside a frozen `build.exe` *is* `build.exe`, not a Python interpreter — using it to shell out would try to run `build.exe -m PyInstaller`. `_python_executable()` falls back to a bare `python` on PATH when frozen, matching `build_exe.bat`'s existing assumption that the correct venv is already active in whatever shell launched it.
- **Missing packages fix themselves once**: `check_environment()`'s PySide6/PyInstaller pre-flight check gets the same frozen-vs-not split (a direct `__import__()` from inside `build.exe` would only see what's bundled in `build.exe` itself, not what the ambient `python` actually has installed) — but rather than just erroring, a missing package first triggers one automatic `python -m pip install -r requirements.txt` (`_auto_install_dependencies()`), and only errors out if that doesn't fix it (no network, no `python` on PATH at all, etc.). So a fresh checkout, or a venv that's drifted behind `requirements.txt`, self-heals on the next `build.exe` run instead of needing a manual `pip install` first.

Net effect: `make_build_exe.bat` once (and again whenever `build_setup.py` changes) produces `build.exe`; running that (or `python build_setup.py` directly) produces a single `Kurulum/setup.exe` with no other files needed alongside it — that's the one file to send to a branch manager, who runs it in an empty folder and answers a few prompts. (`Kurulum` is just the output folder's name — Turkish for "setup/installation" — and carries no other meaning; rename `SETUP_DIST_DIR` in `build_setup.py` if you'd rather call it something else.)

## `prompt_db_path()` rejects a non-absolute answer instead of just warning about it

Both wizards' database-path prompt used to accept ANY typed answer, printing only a soft "doesn't look like an absolute path" warning (`deploy_system.py`) or no warning at all (`installer.py`) before writing it straight into `config.json`. In practice this let a single stray keystroke - e.g. typing `y` at this prompt (easy to do right after the *"...now? [y/N]"* dealership-details question just above it) - silently produce a `config.json` with `"db_path": "y"`. Every app then resolves `get_db_path()` to a relative path, which SQLite creates fresh wherever the app's current working directory happens to be (its own install folder, for a double-clicked `.exe`) - a brand new, empty, completely disconnected database, not the shared one. From the user's side this looks exactly like data loss ("everything I registered just disappeared") rather than an obvious setup mistake, and it's silent by construction: there's no exception anywhere, `sqlite3.connect()` happily creates a new file.

Both `prompt_db_path()`s now loop until the answer is either empty (accept the default/per-app-local behavior) or absolute, re-prompting with an explicit explanation otherwise - see `tests/test_setup_wizards.py`. The absoluteness check deliberately uses `PureWindowsPath(raw).is_absolute()`, not the platform-native `Path`, for two reasons: these wizards only ever target a Windows deployment (see `check_environment()`'s warning) so "absolute" should always mean Windows rules (`C:\...` or a UNC `\\SERVER\share\...`) regardless of what OS happens to be running the script itself; and it's what makes this validation testable at all in this project's (Linux) test environment, where the platform-native `Path` treats `C:\...` as *not* absolute.

## A generated POS terminal registers itself as a dealership

Both setup wizards (`deploy_system.py` and `installer.py`) now ask, right after building/installing any POS instances: *"Enter real dealership details for these N POS terminal(s) now? [y/N]"*. Declining auto-fills a placeholder (`code="POS-<n>"`, `name="POS Terminal <n>"`, `region="Metro"`, `city="Unspecified"`) for every instance; accepting prompts per terminal for exactly the fields `admin_app`'s Dealerships page itself edits — code, name, region (a numbered 1/2/3 choice, not free text, so it can't produce a value `dealerships.region`'s `CHECK` constraint would reject), city, and an optional manager name. Either way, every POS instance ends up with an entry.

**Why this writes a sidecar file instead of the database directly.** Both wizards can run somewhere the shared database *isn't* reachable yet — `deploy_system.py` is a developer's local build machine, and the `db_path` typed into it (or into `installer.py`, on a branch manager's machine) can legitimately be a UNC path meant for a different till than the one currently running the wizard. So neither wizard calls `dealership_repository.create()` itself. Instead, `write_dealership_sidecars()` (present near-identically in both files — see below) writes one `POS_<n>.dealership.json` next to each `POS_<n>.exe`, named via `shared/dealership_bootstrap.sidecar_path_for()` so both the writer and the reader agree on the filename without either hardcoding the other's convention twice. This is the same "travels with the .exe" shape `config.json` already has (see Mass Deployment above) — move `POS_2.exe` to till #2, take `POS_2.dealership.json` along with it.

**Who turns a sidecar into a database row: Admin first, POS as a fallback.** `shared/dealership_bootstrap.apply_sidecar()` is the one function that writes the row; two startup hooks call it:

1. **`register_sidecars_beside_this_exe()`, at the top of `admin_app/main.py`'s `main()`** — applies *every* `*.dealership.json` in the running Admin `.exe`'s own folder. Both wizards put `Admin_1.exe` next to `POS_1..N.exe`, so simply opening Admin right after setup makes every POS terminal from that run appear as an active dealership. This is the path that actually delivers the original requirement ("terminals generated during setup reflect as active dealerships in Admin"). The first version of this feature only had hook 2, which meant nothing appeared in Admin until someone had opened every single POS terminal at least once — after setup, users naturally open Admin to check, saw nothing, and reasonably concluded it was broken (reported several times before this was changed).
2. **`register_pending_dealership()`, at the top of `pos_app/main.py`'s `main()`** — applies that POS instance's *own* sidecar. The fallback for a `POS_N.exe` (+ sidecar + `config.json`) copied out to its own till, away from Admin's folder.

Both are no-ops unless `sys.frozen` is set (mirrors `shared/paths.py`'s `_exe_adjacent_config_path()`, so a `python -m ...` dev run never does this), and neither can raise — a bootstrap hiccup must never stop a cashier opening the till or an admin opening the dashboard.

**"Latest setup wins, then hands off to Admin" — the `applied_at` stamp.** A sidecar freshly written by a wizard has no `applied_at` key. The first app to see it creates the dealership, or — if that code already exists — **updates** the existing row to the sidecar's name/region/city/manager and re-activates it, then writes `"applied_at": "<timestamp>"` back into the sidecar. Every later launch (by Admin or the POS) sees the stamp and leaves the row alone, so edits made afterwards in Admin > Dealerships are never clobbered by a relaunch. Re-running setup overwrites the sidecars with fresh, unstamped ones, so its new details are applied again. The first version was instead idempotent by `code` alone and *never* updated an existing row — so re-running setup with new details for code `001` silently left the old details showing in Admin, which looked exactly like a bug (it was reported as one: "the information I provided during setup differs from this active dealership"). If the stamp can't be written back (read-only folder), that's logged, and the same details are simply re-applied on the next launch. If Admin and a POS apply the same fresh sidecar at the same instant, the loser of the `create()` race gets `DuplicateDealershipCodeError` and falls back to an update with identical values.

**Every outcome is logged to `POS_<n>.dealership.log`** next to the sidecar — `Admin_1.exe: registered '002' ('43')...`, `...: updated '001' with the latest setup details (name was 'North', now '321')`, `...: nothing to do - ... already applied at ...`, or `...: FAILED to register '<code>': <exception>` — each with the exact `db_path` used (read through `database.connection.get_db_path()`, the same reference `get_connection()` uses). The built apps are `--noconsole`, so this file is the only way to see what happened; the prefix says which app did it. The most useful part for a "doesn't show up in Admin" report is that `database:` path: if it differs from the `db_path` in the `config.json` of the Admin being checked, the two apps are simply reading different database files.

**`installer.py` duplicates the small prompt/writer/region-list rather than importing them** — same reasoning as its existing `ROLES` tuple duplicating `build_setup.py`'s `PAYLOAD_ROLES`: this file has zero dependency on the rest of the repo by design (see its own module docstring), so it can't `import shared.models.DEALERSHIP_REGIONS` the way `deploy_system.py` does. Both copies are commented with where their sibling lives, and covered by `tests/shared/test_dealership_bootstrap.py` (Admin-folder registration, POS self-registration, applied-stamp idempotency, fresh-setup updates of an existing code, Admin edits surviving relaunch, missing/corrupt sidecar, invalid region fallback, unreachable database) rather than by testing the CLI prompt text itself twice.

**Deliberately scoped to POS only** — a dealership is a storefront/branch, which is what `pos_app` represents; Depot instances (warehouses) and Admin instances (the management app itself) get no sidecar and no prompt, since neither maps to a `dealerships` row.

**The registered terminal's own header now shows its real identity, too.** `shared/dealership_bootstrap.load_dealership_identity()` is a read-only sibling of `register_pending_dealership()` — same sidecar file, no database write — that `pos_app/gui/main_window.py` calls when building its `PosHeader`: if a sidecar is present, the header's brand name/location show the terminal's actual registered dealership name and `"{city} · {region}"` instead of the generic `DEALERSHIP_NAME = "GPUSA"` / `LOCATION_LINE = "Main Floor · Register 01"` placeholders (a real-but-different substitution, same principle as depot_app Console's Warehouses page showing real SKU stats instead of the mockup's fabricated capacity numbers — there's no "floor/register number" concept in the schema, so city/region stands in for it). Falls back to the placeholders whenever there's nothing to show: dev-mode `python -m pos_app.main` (no `sys.frozen`, so no way to know which instance this is — same reasoning as `register_pending_dealership()`), a built exe with no sidecar next to it, or one that hasn't registered yet.

**The cashier shown is whoever signed in at the till** (see "Sign-in & accounts" below) - never the sidecar's `manager_name`, which is a business contact on file, not the person at this till.

## Purchase Requests / Purchase Orders

**The workflow, end to end.** An administrator sets a safe unit-price band per product (admin_app > Purchase requests > "Safe price ranges"). The depot's purchasing manager raises an order in depot_app's Manager Portal > "01 Purchasing Operations" (product, supplier, quantity, unit price). `purchase_order_repository.submit()` judges the price against the band: inside it, the order is **sent** straight away; outside it (above the ceiling *or* below the floor), or for a product with no band at all, it's **held** (`status = 'pending'`). Held orders appear in admin_app's approval queue, where an administrator **approves** (-> sent) or **rejects** (-> rejected, with an optional reason the depot sees). The depot's banner and table follow the decision on their own within a few seconds (a `PollingTimer` while the portal is open), and admin's "Purchase requests" sidebar badge is the real pending count (another `PollingTimer`, one indexed `COUNT(*)` every 10 s) - it used to be the mockup's hardcoded "4".

**Where each piece came from in the mockups.** The depot form, the read-only "Safe price range · set by Admin" band bar, the in-range / "Out of safe range" / "Below safe range" verdicts, the two submit buttons, the "Awaiting Admin Approval" banner and the PO table are the Warehouse Console mockup's `portalTab: 'purch'`, recreated field for field (`depot_app/gui/purchasing_panel.py`). The admin approval cards are the "Admin action required · Out-of-range purchase requests" dropdown from Inventory Dashboard.dc.html (`admin_app/gui/components/approval_queue.py`). The band editor is Settings.dc.html's "Safe Purchase Price Range". The admin mockup has no Purchase Requests *page* (its nav link is `href="#"`), so `purchase_requests_page.py` assembles those pieces plus an "All purchase orders" history table; Overview gets a real "Pending approvals <n>" header button that opens it (the mockup's version opens a dropdown - one approval queue, not two copies).

**Deliberate choices, each flagged in code:**
- **One rule, two callers.** `shared.models.hold_reason_for(band, price)` decides send-vs-hold. The depot form uses it for its live preview; `submit()` uses it again inside `BEGIN IMMEDIATE` as the authoritative decision, so the preview can never disagree with what's stored and an admin changing a band mid-submit can't produce an order stamped with one band but judged against another. Band ends are inclusive.
- **Per product, not per category.** The Settings mockup frames bands per category, but products have no category field; the depot mockup is per-SKU anyway.
- **No band = held.** Nobody has said what a sane price is yet, so an admin has to look. The depot form says so ("No safe range set") before submitting.
- **Snapshots on the order.** `product_name_at_order`, `range_min`/`range_max` are copied at submission (same idea as `transaction_items.unit_price_at_sale`), so the admin sees exactly what the order was judged against even after the product or band changes.
- **Safe with two admins.** `approve()`/`reject()` are `UPDATE ... WHERE id = ? AND status = 'pending'`; the second decision matches nothing and raises `PurchaseOrderAlreadyDecidedError`, which the page reports in its footer line instead of silently flipping an approval into a rejection.
- **No fabricated identity.** The mockup's "Requested by M. Okafor" has nothing real behind it (no login system), so cards show the supplier and unit price instead. The mockup's "limit $120,000 · +55% over" was a per-site *spend* limit; this app's rule is a per-product *unit-price* band, so that's what's shown ("band 520.00–680.00 / unit · +9% over").
- **Dropped from the mockups:** the depot's "Simulate admin approval" demo button (the admin side is real now), the "Based on the last 90 days of supplier quotes" line (nothing computes bands from quotes), and Settings' per-role approval / manager-tolerance % / escalation timers / notification switches (no login or roles system for them to act on - they'd be switches that do nothing). No currency symbol is invented; amounts are plain `1,612.00` like the rest of the app (`shared.formatting.format_amount`), and the depot's price field accepts both `742,50` and `742.50` (`parse_amount`).
- **Not in this v1:** receiving goods *against* a PO (receiving still goes through `inventory_repository.receive_stock()`; linking a receipt to its PO and marking it received is the natural next step), a suppliers table (supplier is free text with an optional per-product default, as in the mockup's own form), and multiple warehouses (orders are stamped with `depot_app.gui.main_window.WAREHOUSE_SITE`; `site` is plain text, not a FK, like `employees.location_name`).

**Schema migration note.** Both new tables (`purchase_price_ranges`, `purchase_orders`) are `CREATE TABLE IF NOT EXISTS`, so an existing `shared_backend.db` picks them up on the next app launch with its data intact - verified against a copy of Erol's real database. No existing table changed.

**Two small app-wide fixes found while building this.** `shared/gui_kit/icon_kit.py` filled each icon pixmap with `0`, which PySide6 reads as `Qt.color0` - *opaque black* - so every icon in all three apps sat on a black square (invisible on admin's dark theme, visible on depot's and POS's light ones); now `Qt.transparent`. And a lone `&` in a `QPushButton`/tab label is a keyboard-mnemonic marker, so "Treasury & Ledger" rendered as "Treasury  Ledger" in admin's sidebar and depot's portal; labels now escape it as `&&`.

## Treasury & Ledger

**What's stored.** One `ledger_entries` row per financial document: a check, promissory note, bank transfer or invoice, either coming **in** (money owed to us - receivables) or going **out** (money we owe - payables), with document number, counterparty, an optional bank/detail line, issue and due dates, a positive amount, and an optional site (`NULL` = company-level). `database/ledger_repository.py` owns all of it: create/update/delete, `mark_cleared()`, `mark_endorsed()` (only for a *received* check or note passed on to someone else instead of cashed - enforced in the repository and by a CHECK constraint), `reopen()` (a mistake, or a bounced check), and `known_counterparties()` (ledger names + dealership names + purchase-order/price-band suppliers, for type-ahead). The same document number can't be recorded twice for the same direction and type.

**What's computed, not stored.** "Overdue" is derived every time from `due_date` vs. today (`shared/treasury.py`) - the mockups store it as a status, which would make every row wrong the morning after. The same module computes both screens' numbers from the rows: the KPI summary (open receivables split into checks/notes/overdue, open payables into checks/transfers, net position, what's due in the next 7 days), the 30-day milestone data, display statuses ("Open" for an unpaid incoming invoice, the depot mockup's word) and due-date wording ("in 5 days", "3 days overdue", "Settled"). Pure functions over `LedgerEntry`, fully unit-tested, so Admin and Depot can't disagree.

**Admin: `admin_app/gui/pages/treasury_page.py`** recreates Treasury.dc.html: the three KPI cards; "Next 30 days · Payment & collection milestones" as a painted day strip (`components/milestone_strip.py` - green circles for collections, smaller orange ones for payments, sized by amount like the mockup, filled when overdue, weekends dimmed, today and each 1st in gold, hover a day to list its documents); and the document table with its "Received Checks & Notes" / "Issued Checks & Payments" tabs (with counts), All / Pending / Cleared / Overdue filter, due-date sort, "+ Record receipt / payment" (`components/ledger_entry_form_popup.py`, which the mockup's button never had) and "N documents · total" footer. Added because a ledger you can't settle is just a list: Mark cleared / Mark endorsed / Reopen / Edit / Delete on the selected row, and a Site column.

**Depot: `depot_app/gui/treasury_panel.py`** is the Manager Portal's "02 Local Treasury & Ledger" tab, recreated from the Warehouse Console mockup: the four clickable type cells (Checks, Promissory Notes, Payments, Receivables - the depot mockup's names for check / note / outgoing transfer / incoming invoice), the segmented type filter, "Filtered to WH-01 · İstanbul Merkez", the signed-amount table with the inverted "Overdue" tag, and "Net position · shown rows". It shows only this depot's site. It adds "+ Record document" (`ledger_entry_dialog.py`, stamped with the site) so a check or invoice that lands at the depot can be entered there; settling is left to Admin on purpose, since that's where the company-wide ledger is reconciled.

**Deliberately different from the mockups:**
- The milestone strip's line is the running **net of scheduled items starting at 0**, labelled as such - not a "projected balance". The mockup starts that from a made-up $1.84M; no cash or bank balance is recorded anywhere in this system, and inventing one would make every point on the line fiction.
- No "Bank reconciliation last run today, 06:00" footer - nothing reconciles against a bank.
- No "paid this month" under the depot's Payments cell - the total isn't limited to this month, so it says how many aren't settled instead.
- No currency symbol, as everywhere else in the app (compact amounts read "212k", "1.84M").
- **Not in this v1:** opening balances / bank accounts, partial payments, attachments/scans of the actual check, and automatic links to purchase orders or sales (a sent PO is the obvious future source of a payable).

**Migration.** `ledger_entries` is a new `CREATE TABLE IF NOT EXISTS` table; an existing `shared_backend.db` picks it up on next launch with its data intact (verified against a copy of Erol's real database, which already had the purchase-order tables).

**App-wide visual fix found while building this.** `shared/theme.py`'s base stylesheet styles `QFrame` with a surface background and a 1px border - and `QLabel` is a `QFrame` subclass, so *every label in all three apps* sat in its own little bordered box (the stray rectangles around "GPUSA", "ADMIN DASHBOARD", "Admin User", page titles, card captions in the earlier screenshots). The base stylesheet now resets `QLabel` to a transparent background and no border; labels that want one set it themselves, which still wins. The same cascading mistake - a selector-less `setStyleSheet("border-bottom: ...")` on a container, which applies to every child label too - was fixed in `Section`'s header, `StatCard`'s footer, admin's sidebar footer, depot's Console footer, Floor header and Manager Portal session strip (now scoped with `#objectName` selectors). A few depot Floor components (Inbound/Outbound panel captions, the Check-in Log placeholder) still use the selector-less pattern and show faint boxes; left for a focused pass rather than folded into this slice.

## Shipments / Distribution

**The flow across all three apps.** The depot plans a shipment in **Console > Shipments** (`depot_app/gui/shipments_page.py`): destination dealership (active ones only), carrier, driver, ETA, product lines - status `scheduled`. **Dispatch** when the truck leaves (`in_transit`, `departed_at` stamped; or tick "Truck is leaving now" when creating). If it runs late, **Update ETA** - the original promise stays in `planned_eta`, so the lateness shows everywhere. At the dealership, **pos_app > Receive Inventory** (`pos_app/gui/pages/receive_page.py`) lists what's coming to *that* terminal's dealership (its setup-file code), the cashier ticks each line or uses Accept All, or switches to Report Discrepancy to adjust received counts with −/+ and add a note, then completes the receipt (`delivered`). **admin_app > Distribution** (`admin_app/gui/pages/distribution_page.py`) tracks everything. The POS home tile's "N arriving" badge is now the real count (it was a hardcoded 2).

**Stock requests (migration v8).** A dealership asks for stock from **pos_app > My Stock > Request stock** (`pos_app/gui/stock_requests.py`; one open request per shop and product, enforced by a partial unique index) and follows it under **My requests** (waiting / shipment planned / delivered / declined with the reason; a waiting one can be withdrawn). The depot sees them in the **Dealership needs** panel at the top of Console > Shipments (`depot_app/gui/dealership_needs.py`): *Plan shipment* fills the New shipment form with every open request of that shop, and creating the shipment marks them `planned` in the same transaction (`stock_request_repository.mark_planned`); cancelling the shipment puts them back to `open`. *Decline* stores a reason. The panel's second list, `dealership_shortages()`, is every active shop whose shelf is at or below the product's reorder level, with what is already on the way and asked for, so the depot can top it up without waiting to be asked. Admin > Distribution shows both lists read-only.

**`database/shipment_repository.py`** owns `shipments` + `shipment_lines`: `create()` (validates dealership/products, merges duplicate lines, snapshots the dealership and product names), `dispatch()`, `update_eta()`, `cancel()`, `complete_receipt()`, `list_shipments()`, `count_incoming()`. Every status change is `UPDATE ... WHERE status IN (...)`, and `complete_receipt()` checks the status inside its `BEGIN IMMEDIATE`, so two tills completing the same receipt can't both adjust stock - the second is told (`ShipmentStateError`).

**Stock.** *Superseded by the Warehouse slice below* - shipments now move per-location stock: Dispatch takes the lines off the origin warehouse (refused if it's short), Cancel after dispatch puts them back, and the receipt puts the received units on the dealership's shelf, with any discrepancy written off / added as a 'discrepancy' movement. (In this slice's first version stock was one company-wide number and only discrepancies moved it.) Still true: a shipment must NOT also be logged as an Outbound dispatch on the depot Floor - Outbound is for goods leaving the company.

**What's derived, not stored (`shared/distribution.py`).** There's no GPS or carrier feed, so nothing pretends to know where a truck is: **progress** is estimated from the schedule (time since departure over the departure→ETA window, capped at 99% until received); **"Arriving"** = due within the hour; **"Delayed"** = the current estimate is ≥15 min later than promised, either because the ETA was moved or because it has passed and the shipment still isn't in. The same module computes the admin KPIs (items/shipments on the road and origins; delivered today of everything due today; delayed count, average lateness) and ETA wording ("14:55", "Tomorrow 09:30", "Arrived 11:58").

**Mockup fidelity and deliberate differences:**
- **Admin Distribution** recreates the three KPI cards, the "Route tracker · Active routes, warehouse to dealership" rows (`components/route_tracker.py` - covered/remaining track in the status colour, click to select), and the "Live Transit Ledger" with its status filter and row selection synced to the tracker. Replaced: the hardcoded "1,204 items" / "41 of 57" / "avg. 2h 40m late" with the real figures; "Weather on I-81 · 1 carrier breakdown" with the carriers actually running late; "Carrier feeds refresh every 30 s" with a plain statement that progress comes from the schedule. Dropped: the per-route intermediate-stop dots (shipments are single-drop). Added: "Delivered · last 7 days · Receipts & discrepancies", the part an admin has to act on.
- **POS Receive Inventory** is field-for-field the mockup's screen (Incoming cards, Accept All / Report Discrepancy pill, Expected / Received with −/+, "N of M checked · K discrepancies", Complete receipt / Send report & receive). Different: tags are the real derived status ("Arriving", "Delayed", "On the way", "Scheduled", "Received") rather than "At door" - nothing tells the system a truck is physically at the door - and report mode adds an optional note the depot sees. A terminal with no setup file (dev run) lists every dealership's shipments and says so.
- **Depot Console > Shipments** has no mockup page (the Console lists "Shipments" but never drew it), so it's built in the Console's own Industry style. The Console header now names whichever page is open (it used to say WAREHOUSES everywhere).
- **Not in this v1:** multi-drop routes, partial deliveries (a receipt closes the shipment), and linking a shipment to the purchase order or sale it fulfils. (Per-location stock arrived with the Warehouse slice.)

**Migration.** `shipments` and `shipment_lines` are new `CREATE TABLE IF NOT EXISTS` tables - verified against a copy of Erol's real database. The dealership on a shipment is a snapshot (code + name), not a foreign key, so deleting or renaming a dealership never rewrites shipment history.

## Warehouses & per-location stock

Erol's two decisions for this slice: **full per-location stock** (every warehouse and every dealership holds its own stock; a POS sale comes off its dealership's shelf; shipments move stock between places) and **the setup wizard asks** for each Depot's warehouse details, the same way it asks for each POS's dealership.

**The model.** New `warehouses` table (`code` "WH-01" as natural key, name, city, `capacity_units` - NULL until set -, `docks`, `is_active`) and **`stock_levels`** - one row per (location, product): `location_kind` is `'warehouse'`, `'dealership'` or `'unassigned'`, `location_code` the warehouse/dealership code ('' for unassigned). `shared.models.StockLocation` (frozen; `StockLocation.warehouse("WH-01")`, `.dealership("001")`, `UNASSIGNED`) is how every layer names a place. `products.stock_quantity` stays, as the **company total**, and the invariant every write keeps inside its own transaction is:

> `products.stock_quantity` = SUM(`stock_levels`) + units on dispatched, not-yet-received shipments

So there are exactly two kinds of change (`database/stock_repository.py`, the only place SQL for `stock_levels` lives, and now also the writer of `stock_movements`): stock **entering or leaving the company** moves a level *and* the total (depot Inbound/Outbound, a POS sale, a stock count, a receipt discrepancy); stock **moving inside the company** moves levels only (a transfer, loading a shipment). `tests/stock_invariant.py` asserts the equation after every stock test.

**Where each app's stock now comes from / goes to:**
- **pos_app** works on its dealership's shelf (`StockLocation.dealership(code)` from its setup file; a terminal without one works on UNASSIGNED). New Sale shows and caps at local quantities, `finalize_transaction(transaction, location)` validates against the shelf (summed per product, so the same barcode on two lines can't slip past) and stores `transactions.dealership_code`; My Local Stock and the Home "out/low" badges are local; every completed receipt now refreshes them.
- **depot_app** *is* one warehouse (below). Floor Inbound/Outbound log against it (`inventory_repository.receive_stock/dispatch_stock(..., location=)` - kept as a facade), the Low Stock banner reads its levels (one critical level per product, applied at every location), Console > Shipments stamps `origin_code` and its product picker shows "N here".
- **Shipments** (`shipment_repository`): dispatch takes lines off the origin (`InsufficientStockError` names the location; nothing written), `stock_moved` = 1 while the goods are on the truck, cancel returns them, receipt puts the received quantity on the dealership shelf and books any difference as a `discrepancy` movement. A shipment received without ever being dispatched is taken off the origin at receipt time (as far as the origin's records go - the gap is noted). Shipments planned before this slice have no `origin_code` and draw from UNASSIGNED.
- **admin_app** gets the real **Warehouses** page (below); Inventory's detail panel lists where a product is (per warehouse / dealership / unassigned / on the road); Dealerships' detail shows its real stock on hand. Deleting a warehouse or dealership that still holds stock is refused (`LocationHasStockError`).

**Upgrading an existing database (migration v1).** Adds `stock_movements.location_kind/location_code/reason/reference`, `transactions.dealership_code`, `shipments.origin_code/stock_moved`; marks shipments already in transit as `stock_moved`; and turns each product's old company-wide quantity, minus what's on those trucks, into an **UNASSIGNED** level - nothing ever recorded where those units physically are, so the system says so instead of guessing. Admin > Warehouses shows an "N units aren't at any warehouse or dealership yet" banner with **Place all here** (one warehouse) and **Move / count stock** for splitting them. **Consequence to know on day one: until stock is placed, dealerships have 0 on their shelves and POS can't sell it** - that's the honest reading of "per-location", and it's one click to fix. New products entered in Inventory with a starting stock also start UNASSIGNED (the form doesn't ask where).

**Setup wizard → warehouse (`shared/warehouse_bootstrap.py`).** Same design as the dealership sidecars: `deploy_system.py` and `installer.py` ask per Depot instance for code / name / city / capacity (units, optional) / docks (or fill WH-01, WH-02, … placeholders) and write `Depot_N.warehouse.json`; Admin applies every one in its folder at startup, each Depot applies its own; "latest setup wins, then hands off to Admin" via the `applied_at` stamp; outcomes in `Depot_N.warehouse.log`. `resolve_this_depot_warehouse()` is how the depot knows which warehouse it is - its sidecar's code, else the first active warehouse, else a new "WH-01 · Main warehouse" - and its `site_label` ("WH-01 · İstanbul Merkez") replaces the old hardcoded `WAREHOUSE_SITE` on purchase orders, ledger documents and shipments.

**Admin > Warehouses (`admin_app/gui/pages/warehouses_page.py`)**, recreated from Warehouses.dc.html: the KPI row (warehouses, units in warehouses vs. set capacity, "Near capacity · 85% threshold", plus unassigned stock), one card per warehouse (`components/warehouse_capacity_card.py`: name, status pill - "Near capacity" at ≥85%, else "Operational" -, city · code · docks, capacity % with the bar and a threshold tick, used / capacity units, on shift / rostered, inbound / outbound today); clicking a card filters the tabs to that site (again to clear). **Movement Logs** (Time, Check-in/Check-out, SKU, Product, Qty, Site, Why, Reference; All/Inbound/Outbound) and **Workforce Attendance** (today's roster per warehouse) are the mockup's tabs; **Stock by location** (every product per warehouse, at dealerships, unassigned, on the road, company total) is added. Header: Add warehouse (`warehouse_form_popup.py`), **Move / count stock** (`stock_move_popup.py` - a transfer between any two places, or a count that sets a level and logs the difference), Refresh; the page polls every 15 s while open. **Depot Console > Warehouses** now shows the same real cards in Industry style (`depot_app/gui/components/warehouse_card.py`, this depot's marked "THIS DEPOT"), with clicking a card switching the read-only movement log.

**Deliberate differences from the mockups:** capacity is **units of stock**, not pallets (nothing records pallets); **docks** is how many a warehouse has, not "6/8 in use" (nothing tracks dock occupancy); the log has **no "Handled by"** column (movements don't record who - the Floor has no sign-in yet); an employee belongs to a warehouse when their free-text Location is its code, name or site label (matched ignoring case and Turkish/accented letters - `shared/warehousing.works_at`), and the Workforce tab lists warehouse employees whose Location matches none.

**Not in this slice:** bins/put-away locations inside a warehouse, per-location reorder levels, and transfers between warehouses by truck (use a shipment to a dealership, or Move for an on-paper correction). Who-did-it on movements arrived with the sign-in slice below.

## Sign-in & accounts

Erol's decisions: sign-in **per role** (Admin needs an administrator at startup; a POS till needs a cashier, with "Switch" at shift change; the depot Floor stays an open kiosk, but its "İdari Giriş" needs a depot manager for the Manager Console, and the Manager Portal asks that person's PIN again and keeps its 10-minute auto-lock); **employee badge + PIN**; and the **first administrator is created on a one-time screen in Admin**, never in setup files.

**Model.** `accounts` (one per employee: `role` admin / depot_manager / cashier, `pin_hash`, `is_active`, `failed_attempts`, `locked_until`, `last_sign_in_at`) and `auth_events` (every sign-in, sign-out, wrong PIN, lockout, refusal, PIN confirmation and account change, with badge, area and terminal - plain text so it outlives the account). Rules live in **`shared/auth.py`** (pure): roles and what each may open (`ALLOWED_ROLES`: admin → Admin, depot Console, POS; depot_manager → depot Console; cashier → POS), PIN rules (digits, 4-12, 6+ for administrators, no repeated/running sequences), hashing (salted PBKDF2-HMAC-SHA256, 200,000 rounds, stored self-describing as `pbkdf2_sha256$rounds$salt$hash`, compared in constant time - standard library only), lockout (5 wrong PINs → locked 5 minutes; an administrator can unlock sooner), and the `Session` / `Actor` objects. **`database/account_repository.py`** is the one door: `authenticate(badge, pin, area, terminal)` checks the lock, the PIN, then - only after a correct PIN, so a wrong badge and a wrong PIN look identical - whether the account/employee is active and the role may open that area, logs the outcome and returns a `Session`. An unknown badge still does a full-cost hash, so timing doesn't reveal which badges exist. **The last active administrator can't be demoted, switched off, removed, or have their employee record deactivated/deleted** (`LastAdminError`), so Admin can never lock itself out.

**Who-did-it (migration v2).** `stock_movements.handled_by`, `transactions.cashier`, `purchase_orders.raised_by` / `decided_by` - "Name · badge" text snapshots (`Actor.label`), so renaming or deleting the employee never rewrites history. Repositories take the actor explicitly (`actor=` / `cashier=` / `raised_by=` / `decided_by=`); the GUI reads it from **`shared/current_session.py`** (one signed-in person per app process). The depot Floor deliberately passes none - it's an open kiosk, and a manager signed into the Console on the same PC isn't the person at the Floor - so its movements show "—". Admin's and the Console's Movement Logs now have the mockup's "Handled by" column; purchase orders show raised/decided by on hover.

## Engineering conventions carried through this codebase

- **Builder reuse**: every builder function (receipt, report) is called verbatim by every consumer — on-screen preview, single-item export, multi-item export. A second output format is a new parameter, never a duplicated function.
- **No overlay positioning**: action buttons live inside the content area they act on (`VisualTab.set_controls()`), never absolute-positioned on top of other interactive elements.
- **Exports fit their content**: the receipt's width is fixed to `RECEIPT_WIDTH_CHARS` (matching actual thermal paper), not stretched; report page size follows `REPORT_PAGE_SIZE`. Any letterhead/branding is one shared function called by every export path.
- **i18n from day one**: all UI strings go through `shared.i18n.tr()`, never hardcoded inline.
- **Comment the why**: non-obvious layout/positioning decisions get a comment noting what was tried and rejected, so a later change doesn't reintroduce a fixed bug.
- **Test isolation**: `tests/conftest.py` builds every test database fresh from `schema.sql` in a temp file — no test ever touches the real `shared_backend.db`. GUI tests use `pytest-qt` and skip cleanly with no display available.
- **Regression test naming**: each test file carries `TODO` notes naming the specific behavior/bug each planned test guards against, so a future failure says what broke.
- **Incremental delivery**: this scaffold ships the data models, constants, theming, i18n, and the WAL-mode connection layer as working code. Repository queries, GUI screens, builders, and exporters are stubbed with `NotImplementedError` and get filled in one tested slice at a time, starting with `database/product_repository.py` + its tests.
- **No cross-app imports**: `pos_app`, `depot_app`, and `admin_app` depend only on `shared/` and `database/`, never on each other — see the layering rule under Layers above.
